# Система управління бібліотекою

Клієнтський застосунок для обліку книг і користувачів, позичання та повернення книг.
Лабораторна робота №2 з предмету «Клієнтські веб-системи».

**Демо:** https://arthur-tubus.github.io/client-app-for-library-management/

## Можливості

- додавання й видалення книг та користувачів;
- позичання і повернення книг, ліміт: не більше 3 книг на користувача;
- валідація форм (обов'язкові поля, ID лише цифри, рік за регулярним виразом);
- сповіщення через модальні вікна (без `alert`);
- пошук книг за автором або назвою;
- пагінація списків (5 елементів на сторінку);
- збереження даних у LocalStorage.

## Технології

TypeScript (класи, інтерфейси, generics, модулі, namespace), Bootstrap 5, Mocha + Chai,
ESLint + Prettier, Husky, webpack (гілка `main`), Vite (гілка `vite-migration`).

## Запуск

```bash
npm install
npm start        # dev-сервер на http://localhost:9000
npm run build    # продакшн-збірка в dist/
npm test         # юніт-тести
npm run lint     # ESLint
npm run deploy   # публікація на gh-pages (гілка vite-migration)
```

## Архітектура

Код розділений за шарами відповідальності:

- `src/models` — класи й інтерфейси даних (`Book`, `User`), без залежності від UI;
- `src/services` — бізнес-логіка: `Library<T>`, `LibraryService`, `Storage`, `NotificationService`;
- `src/utils` — допоміжні функції: namespace `Validation`, пагінація, форматування, генератор ID;
- `src/ui` — єдиний шар, що працює з DOM; уся розмітка генерується з коду;
- `tests` — юніт-тести для `Library`, `LibraryService`, `Validation`, `paginate`.

У `index.html` лише `<div id="app"></div>`. У версії на Vite додатково є тег
`<script type="module">`: це підключення точки входу, а не розмітка інтерфейсу.

## Робочий процес

- Feature branch workflow: кожна задача в окремій гілці (`feature/...`), потім злиття в `main`.
- Conventional Commits (`feat:`, `fix:`, `chore:`, `build:` тощо).
- Husky: перед кожним комітом автоматично запускаються ESLint і тести Mocha.
- Міграція на Vite виконана в окремій гілці `vite-migration`, `main` зберігає версію на webpack.

## Висновок: webpack проти Vite

Заміри зроблені на цьому проєкті (Windows, TypeScript, Bootstrap 5, невеликий SPA).
webpack 5.112 на гілці `main`, Vite 8.3 на гілці `vite-migration`.

| Показник                          | webpack   | Vite        |
| --------------------------------- | --------- | ----------- |
| Холодний старт dev-сервера        | 4,9–8,8 с | 0,32–0,49 с |
| Оновлення після зміни файла (HMR) | 0,46 с    | [...]       |
| Продакшн-збірка                   | 8,72 с    | 3,32 с      |
| Розмір `dist`                     | 328,8 КБ  | 323,4 КБ    |

**Швидкість.** Vite запускається в 10–20 разів швидше: він не збирає весь бандл перед стартом,
а віддає модулі браузеру по запиту (нативні ES-модулі), а залежності попередньо збирає esbuild.
webpack на старті збирає все повністю, тому час зростає разом із проєктом.
Продакшн-збірка у Vite також швидша, хоча тут різниця менша (приблизно у 2,6 раза).

**Розмір збірки.** Практично однаковий, бо основну частину займає Bootstrap, а не код застосунку.
Для малого проєкту вибір збірника на розмір не впливає.

**Складність налаштування.** У webpack потрібно було самостійно описати `entry`, `output`,
правила для `ts-loader`, `css-loader`, `sass-loader`, `style-loader`, плагін `HtmlWebpackPlugin` і `devServer`.
Для Vite вистачило короткого `vite.config.ts` (порт, `base`, папка збірки): TypeScript і
стилі працюють без додаткових loader'ів. Знадобилося лише явно підключити скрипт у `index.html`.

**Підключення UI-фреймворку й TS.** Bootstrap у обох випадках імпортується в `index.ts`.
У webpack для цього потрібен ланцюжок loader'ів, у Vite CSS і SCSS обробляються самі
(потрібен лише пакет `sass`).

**Нюанси.** Vite лише прибирає типи (esbuild) і **не перевіряє їх**, на відміну від
`ts-loader`, тому в скрипт збірки додано `tsc --noEmit`. Також довелося вказати
`--configLoader runner`, щоб прибрати попередження про ESM-конфіг у CommonJS-проєкті.

**Екосистема.** У webpack більша і старіша екосистема плагінів та loader'ів, він гнучкіший
для нестандартних сценаріїв. У Vite плагінів менше, але для типового SPA їх достатньо,
а конфігурація простіша.

**Суб'єктивна оцінка.** Для невеликих SPA-проєктів, подібних до цього, Vite зручніший:
швидкий старт, мінімум конфігурації, менше залежностей у `package.json`. webpack має сенс,
коли потрібен тонкий контроль над збіркою або в проєкті вже налаштована складна конфігурація.
